## 0. 这节课要解决什么

上一节（02）解决的是"**把话说清楚**"；这一节更进一步：**与其费力描述，不如直接给模型一个示例。**

术语先记住：

| 说法 | 意思 |
| --- | --- |
| 零样本 zero-shot | 只给任务描述，不给示例 |
| 单样本 one-shot | 给 1 个示例 |
| **少样本 few-shot** | 给 2~5 个示例（本节主角） |

本节课的任务很实用：**从一句话里抽取结构化信息（时间 / 地点 / 人物），输出 JSON。**

> 一句话总结：**示例的作用主要是"定格式"**，这一点下面有实测数据支撑。

## 2. 提示词的四个零件

老师的代码把这四样分开定义，最后拼成一个 `prompt`，这个拆法非常好用，建议照抄：

| 零件 | 老师代码里的变量 | 作用 |
| --- | --- | --- |
| 任务描述 | `instruction` | 说明"要做什么"：提取 time / location / person |
| **示例** | `example` | **"少量样本"里的"样本"**，示范输出长什么样 |
| 待处理输入 | `input_txt` | 真正要分析的那句话 |
| 格式限制 | `output` | 规定"怎么答"：以 JSON 格式输出 |

组装（`f-string` 把变量填进大括号）：

```python
prompt = f"""{instruction}

{example}

现在请处理下面这条输入：
{input_txt}

{output}"""
```

运行本项目代码，打印出来的提示词原文：

```
你的任务是识别用户输入的信息，提取信息中的时间(time)、地点(location)、人物(person)

示例：
    在本周三，我和张三一起去长沙世界之窗玩了一下
    {"time": "本周三", "location": "长沙世界之窗", "person": "我和张三"}

现在请处理下面这条输入：
我计划着周末和小丽一起去爬岳麓山，本来还想带张三一起去，但是他要工作，所以就算了

限制：以JSON格式进行输出，不要输出任何解释文字
```

> **提示**：调试 prompt 时，**先把拼好的 prompt 打印出来看一眼**（本项目代码第 1 步就是这么做的）。很多"模型怎么这么蠢"，其实是提示词拼错了、或者变量没填进去。

## 3. 完整代码（`03.prompt少量样本.py` 的核心部分）

```python
import json
import os
import sys

if hasattr(sys.stdout, "reconfigure"):        # 防 emoji 崩（见 02 笔记）
    sys.stdout.reconfigure(errors="replace")

from dotenv import load_dotenv
from openai import OpenAI

THINKING = "disabled"
MODEL = "deepseek-flash"

load_dotenv(override=True)
api_key = os.environ.get("DEEPSEEK_API_KEY")
if not api_key:
    raise SystemExit("没有读到 DEEPSEEK_API_KEY，请确认项目目录下有 .env 文件。")

client = OpenAI(api_key=api_key, base_url="https://api.deepseek.com")

instruction = "你的任务是识别用户输入的信息，提取信息中的时间(time)、地点(location)、人物(person)"
example = """示例：
    在本周三，我和张三一起去长沙世界之窗玩了一下
    {"time": "本周三", "location": "长沙世界之窗", "person": "我和张三"}"""
input_txt = "我计划着周末和小丽一起去爬岳麓山，本来还想带张三一起去，但是他要工作，所以就算了"
output = "限制：以JSON格式进行输出，不要输出任何解释文字"

prompt = f"""{instruction}

{example}

现在请处理下面这条输入：
{input_txt}

{output}"""

res = client.chat.completions.create(
    model=MODEL,
    messages=[{"role": "user", "content": prompt}],
    extra_body={"thinking": {"type": THINKING}},
)
print(res.choices[0].message.content)
```

## 4. 实测：示例到底改变了什么？

同一条输入、同一个模型（`deepseek-flash`，思考关闭），只差"给不给示例"：

| 跑法 | 输入 tokens | 输出 tokens | 模型给的结果 |
| --- | --- | --- | --- |
| **少样本**（给了示例） | 110 | 24 | `{"time": "周末", "location": "岳麓山", "person": "我和小丽、张三"}` |
| **零样本**（不给示例） | 69 | 22 | `{"time":"周末","location":"岳麓山","person":["我","小丽","张三"]}` |
| 再跑一次零样本（另一个样本） | 69 | 20 | `{"time":"周末","location":"岳麓山","person":["小丽","张三"]}` |

**关键差别不是内容，而是 `person` 的类型：**

- 给了示例 → `person` 是**字符串**（示例里就是字符串 `"我和张三"`，模型照着学）
- 不给示例 → 模型自己决定，`person` 变成**数组** `["我","小丽","张三"]`

> 这对写代码的人影响很大：如果你的程序后面要 `data["person"]` 拼接成一句话，字符串能直接拼，数组就会报错；反过来要遍历，数组才方便。
> **示例的价值就在这里 —— 它不是教模型"做事"，而是替你把"输出长什么样"钉死。**

顺带一个成本观察：少样本多花 41 个输入 token，换来的是**格式可控**。这笔买卖对需要程序化处理结果的场景非常划算。

## 5. 模型给的 JSON，要真的解析一遍才算成功

模型经常把 JSON 包在 ```` ```json ```` 代码块里，或者前后加一句"好的，结果如下"，直接 `json.loads` 会失败。所以先剥外壳：

```python
def extract_json(text: str) -> str:
    t = text.strip()
    if t.startswith("```"):
        t = t.split("\n", 1)[1] if "\n" in t else t   # 去掉第一行 ```json
        t = t.rsplit("```", 1)[0]                     # 去掉结尾的 ```
    return t.strip()

data = json.loads(extract_json(answer))
print(data["time"], data["location"], data["person"])
```

本机实测解析结果：

```
JSON 解析成功，可以直接拿去用：
    time = 周末
    location = 岳麓山
    person = 我和小丽、张三
```

**这一步才是"能用的标志"** —— 打印出来看着像 JSON，不等于程序能解析。做作业时把 `json.loads` 加上，才算真的完成了"信息抽取"。

## 6. 实测：少样本不是万能的（两个反直觉发现）

### 发现一：同一个提示词，两次结果可能不一样

用**完全相同的**少样本提示词再跑一次，`person` 变了：

| 第几次 | 输出 |
| --- | --- |
| 第 1 次 | `"person": "我和小丽、张三"` ← 把张三算进去了 |
| 第 2 次 | `"person": "我和小丽"` ← 正确排除张三 |

原文明确说了张三去不了（"但是他要工作，所以就算了"）。两次结果不一致，说明 **模型输出带随机性**。

用本项目代码（第 5 步）**连跑 3 次**的真实结果：

```
第 1 次：{"time": "周末", "location": "岳麓山", "person": "我和小丽、张三"}   ← 错
第 2 次：{"time": "周末", "location": "岳麓山", "person": "我和小丽、张三"}   ← 错
第 3 次：{"time": "周末", "location": "岳麓山", "person": "我和小丽"}          ← 对
```

同一个提示词，**3 次里 2 次是错的**。如果只跑一次就下结论，很可能得出"这个提示词很好"的错误印象。

**所以：** 重要任务别只看一次结果。跑 3~5 次看稳不稳定，或者把规则写进提示词、再用代码校验兜底。
这就是为什么做 AI 应用时，**"人工检查 + 程序校验"永远不能省**。

### 发现二：开"思考模式"这次反而答错了

同一提示词，只把思考模式打开（`reasoning_effort="high"`）：

| 设置 | 输出 tokens | 结果 |
| --- | --- | --- |
| 思考关闭 | 22 | `"person": "我和小丽"`（对） |
| 思考开启 high | **412** | `"person": "我、小丽、张三"`（错，多算了张三） |

**结论**：思考模式不是万能药，它增加推理预算**不等于**更准；这里真正的区别来自随机性。要提升准确率，更靠谱的做法是：把规则说清楚 + 加示例 + 用代码校验，而不是盲目把思考拉满（还贵了 18 倍）。

### 三种"改进方案"的实测（都试了）

| 方案 | 输入 tokens | 结果 |
| --- | --- | --- |
| A 原样 | 110 | `我和小丽` ✅ |
| B instruction 里加一句"只提取实际去的人" | 142 | `我和小丽` ✅ |
| C 给两个示例（第 2 个示例专门演示"排除某人"） | 155 | `我和小丽` ✅ |
| D 开思考模式 | 136 | `我、小丽、张三` ❌ |

三种提示词写法这次都对了 —— 但**样本只有一次，不能就断言哪个更好**。这本身也是要记住的一课：**别用一次运行的结果给 prompt 下结论。**

## 7. 什么时候该用少样本

**适合：**

- 输出格式很讲究：JSON、表格、固定话术、工单模板
- "照着做"的活儿：抽取字段、意图分类、格式转换、翻译风格统一
- 用文字很难描述清楚的风格（比如"像客服那样说话"）—— 给两个例子比写两百字说明有效

**不适合：**

- 需要推理的题（该用思考模式，`reasoning_effort` 调档）
- 事实性问答（模型不知道的，给多少示例也编不出来）
- 示例本身有错的情况 —— 模型会**连错一起学**

## 8. 代码编写报错原因以及解决办法

| 报错信息（关键词） | 原因 | 解决办法 |
| --- | --- | --- |
| `SyntaxError: invalid syntax. Perhaps you forgot a comma?` | 字符串里又用了同种引号：`print("……正是"格式限制"要解决的问题")` —— **本次写这两节代码时我自己踩了两次** | 外层双引号里改用单引号或中文书名号 `「」`；或把内层引号转义 `\"` |
| `json.decoder.JSONDecodeError` | 模型输出里有 ```json 代码块或额外解释文字 | 先用第 5 节的 `extract_json()` 剥外壳，再 `json.loads` |
| `KeyError: 'person'` | 模型这次没输出该字段（字段名被改成中文，或漏了） | 用 `data.get("person")` 兜底；或在提示词里把字段名写得更死 |
| `SyntaxError` 且在 f-string 的花括号处 | f-string 里想输出**字面量**花括号 `{ }`（比如直接在 f-string 里写 JSON 示例） | 双写：`{{ }}`；**更省事的做法是把示例存成普通字符串变量**（老师就是这么干的） |
| `UnicodeEncodeError: 'gbk' ...` | 模型回复带 emoji | 脚本开头 `sys.stdout.reconfigure(errors="replace")`（见 02 笔记） |
| 提示词里变量没被替换 / 拼出一堆 `{}` | 用了普通字符串而不是 f-string，或者变量名拼错 | 写成 `f"""...{变量}..."""`，并 `print(prompt)` 检查拼好的结果 |

其余（依赖、密钥、思考模式空回复等）见 day01 笔记第 6 节。
